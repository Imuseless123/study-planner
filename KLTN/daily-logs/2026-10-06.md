```

GET    /api/subjects/{id}      - Get one
PUT    /api/subjects/{id}      - Update (NEW)
DELETE /api/subjects/{id}      - Delete
```

## 4. Điểm kỹ thuật đáng chú ý

### 4.1. Partial update pattern

Sử dụng `model_dump(exclude_unset=True)` thay vì `exclude_none=True`:

```python
updates = req.model_dump(exclude_unset=True)
```

- `exclude_unset=True`: chỉ lấy fields client **thực sự gửi lên** (dù giá trị là null)
- `exclude_none=True`: bỏ qua fields có giá trị null (dù client gửi)

→ Chọn `exclude_unset` vì đó là semantic đúng cho PATCH/PUT: chỉ update cái user muốn đổi.

### 4.2. Repository update linh hoạt

```python
def update(self, subject, **fields):
    for key, value in fields.items():
        if value is not None and hasattr(subject, key):
            setattr(subject, key, value)
    self.db.commit()
```

- `hasattr()` check để tránh set field không tồn tại
- `value is not None` để tránh ghi đè bằng None (dù schema đã filter)

### 4.3. Frontend modal reuse

Dùng 1 modal cho cả create và edit, phân biệt bằng state `editingSubject`:
- `editingSubject === null` → create mode (title "Tạo môn học mới", button "Tạo")
- `editingSubject !== null` → edit mode (title "Sửa môn học", button "Cập nhật")

Giảm code duplication, UX nhất quán.

### 4.4. Statistics tính ở client

4 cards (Tổng, Khó, Ưu tiên cao, Độ khó TB) tính từ `subjects` array ở frontend:
- Tránh thêm endpoint `/api/subjects/stats`
- Data nhỏ (chục môn) → không cần optimize
- Nếu sau này có hàng trăm môn → chuyển sang backend aggregation

### 4.5. Cascade delete warning

Popconfirm warning rõ ràng: *"Xóa môn sẽ xóa tất cả phiên học và bài tập liên quan"* — user biết hậu quả trước khi xác nhận. Backend đã có `ON DELETE CASCADE` nên data integrity được đảm bảo.

## 6. Bài học kinh nghiệm

### 6.1. Về RESTful design

- **PUT partial update** là pattern phổ biến, nhưng thực tế chuẩn REST khuyến nghị:
  - `PUT`: replace toàn bộ resource (client phải gửi đầy đủ fields)
  - `PATCH`: partial update (chỉ gửi fields cần đổi)
- Trong project này tôi dùng `PUT` với partial semantics — pragmatic choice cho prototype. Nếu muốn chuẩn, đổi thành `PATCH`.

### 6.2. Về error handling

- Backend trả **422 Unprocessable Entity** khi request có body rỗng cho PUT (không có field nào để update) — client nhận message rõ ràng.
- `exclude_unset` giúp phân biệt: client gửi `{"subject_name": null}` (muốn xóa name — không hợp lệ) vs client không gửi field name (giữ nguyên).

### 6.3. Về UX table

- **Filter + sort cùng lúc** hoạt động tốt với Ant Design Table
- **Popconfirm cho destructive action** là best practice — không bao giờ xóa trực tiếp
- **Cascade warning** giúp user hiểu consequence trước khi action
- **Empty state + Alert** giúp onboarding user mới

### 6.4. Về test

- Test backend bằng curl trước khi test UI giúp tách biệt bug (backend vs frontend)
- Verify database sau test đảm bảo data integrity (không có orphan records)
- Partial update cần test **2 cases**: gửi 1 field (chỉ đổi field đó) + gửi tất cả fields (replace)
